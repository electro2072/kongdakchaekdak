### 📌 G14 / D2 — gender는 FE가 BE에 맞춘다

**단순 대소문자 문제가 아니다.** 세 번째 값은 단어가 다르다.

| FE | BE |
|---|---|
| `male` | `MALE` — 대소문자만 |
| `female` | `FEMALE` — 대소문자만 |
| `unspecified` | **`NONE`** — 단어가 다름 |

→ `toUpperCase()`만 붙이면 `UNSPECIFIED`가 되어 여전히 깨진다.

**FE가 맞추는 이유:**
1. `User.gender`가 `@Enumerated(EnumType.STRING)`이라 DB에 `MALE`/`FEMALE`/`NONE`이 **이미 저장돼 있다.** BE 변경 = 데이터 마이그레이션
2. `@Column(length = 10)`인데 `UNSPECIFIED`는 11자 → DDL 변경까지 필요
3. FE는 상수 파일 하나. 저장된 데이터도 스키마도 없다

**수정 범위: `services/userApi.ts` 한 파일.**
`GENDER_OPTIONS`의 키(`unspecified`)는 **그대로 둔다** — 서버 명명이 UI 코드로 새면 안 된다. 변환은 API 경계에서.
현재 인바운드 매핑(`mapGenderResponseToKey`)은 값이 틀렸고 **아웃바운드 매핑은 아예 없다**(`JSON.stringify(fields)` 그대로 전송). 양방향 다 필요.

⚠️ **`unspecified`는 `null`이 아니라 `"NONE"`으로 보낼 것.** `interests`와 동일한 규약(`null` = 변경 없음)이
gender에도 적용되므로, `null`을 보내면 "성별을 안 바꾸겠다"가 된다 → **사용자가 "선택 안 함"으로 되돌릴 수 없다.**
⚠️ **BE 응답이 `null`인 경우도 있다.** `gender` 컬럼은 nullable이라 미저장 사용자는 `null`. `NONE`과 구분할 것.

**BE는 건드리지 않는다.** 백엔드 세션 프롬프트에 "`Gender.java` 수정 금지"를 명시할 것.
G17에서 소문자 통일 시 이 매핑 테이블은 값만 바꾸면 되고(3줄), 통일 후에는 사실상 불필요해진다.

**테스터 재검증 조건:**
1. 성별 "남성" 선택 → 저장 → 재시작 → 유지
2. **다시 "선택 안 함"으로 변경 → 저장 → 재시작 → 유지** ← `NONE` 왕복 확인. **2번이 핵심**
3. logcat `알 수 없는 gender 값` 경고 0건

### 📌 G17 배경 — BE 내부부터 규칙이 갈려 있다

경계를 넘는 enum 8개의 직렬화 규칙이 **3가지**다.

| 나가는 형태 | enum | 방식 |
|---|---|---|
| **소문자** | `ShareScope` · `SharePlatform` · `ShareTargetType` · `ShareType` · `DashboardPeriod` | `@JsonValue toLowerCase()` |
| **대문자** | `Gender` · `BookStatus` | `@JsonValue` 없음 |
| **한글 라벨** | `Genre` | `label` 필드 |

`gender`는 "`@JsonValue`를 안 붙인 쪽"이었을 뿐이고, FE는 소문자로 나가는 다수를 보고 추측했다가 틀렸다.
`BookStatus`는 더 나가서 **요청은 소문자, 응답은 대문자**다 — `BookController.search`에 `status.toUpperCase()` 임시코드가 있다.

**목표: 소문자로 통일.** 이미 5:2로 다수이고 `@JsonValue`를 2곳에 붙이면 끝난다.
**`Genre`는 예외로 유지한다** — 한글 라벨이 UI에 그대로 뿌려지고, DB에도 `GenreConverter`로 한글이 저장돼 있으며,
FE `INTEREST_OPTIONS`와 `genreColors.ts`가 한글 키로 색을 고정 매핑 중이다. 바꾸면 마이그레이션까지 번지고 얻는 게 없다.

⚠️ **G13보다 먼저 하면 안 된다.** `BookStatus`를 소문자로 바꾸면 이미 **정확히** 짜인 FE 코드가 깨진다:
```ts
export type BookStatusResponse = 'READING' | 'DONE';
status: book.status === 'DONE' ? 'done' : 'reading',
```
`libraryApi.ts`·`LibraryContext.tsx`는 지금 G13 조사 대상이다. 같은 파일을 건드리면
"버그가 원래 있던 건지 방금 만든 건지" 구분이 안 된다.

**필드 이름(카멜케이스)은 이미 통일돼 있다.** Jackson 기본값이라 저절로 맞았다. 정리 불필요.

### 📌 G18 배경 — 계약의 단일 출처가 없다

`build.gradle`에 **springdoc-openapi가 이미 들어 있고**(`2.5.0`), 컨트롤러 8개 전부에 `@Operation`이 붙어 있으며
`application.yml`에 `/swagger-ui.html` 경로까지 설정돼 있다. **서버를 띄우면 지금도 `/v3/api-docs`에서
실제 코드에서 생성된 스펙이 나온다.** "인터페이스 파일"은 이미 존재하며, 꺼내오기만 하면 된다.

FE가 소통을 안 한 게 아니다. `libraryApi.ts`의 `BookStatus`는 **제대로 맞춰놨다.**
문제는 `userApi.ts`의 이 주석이다:
> *"백엔드 gender 값 형식이 재확인되기 전까지는 알려진 3개 키만 신뢰하고..."*

**확인할 곳이 없어서 주석에 유보를 달고 추측한 채 배포한 것이다.** 한 번 맞춰도 단일 출처가 없으면 또 어긋난다.

⚠️ **springdoc이 `@JsonValue`를 항상 완벽히 반영하지는 않는다.** 스펙을 받은 뒤 위 enum 8개의 값이
실제 응답과 맞는지 눈으로 대조할 것. 안 맞으면 `@Schema(allowableValues=...)`로 명시.
