## 3. 엔티티 설계 매핑 (테이블정의서 기준 + 신규 변경분)

| 테이블 | 우선순위 | 비고 |
|---|---|---|
| User | 1순위 | 소셜 로그인 붙기 전엔 임시 로그인(이메일/PW)으로 먼저 CRUD 검증. **`gender` 컬럼 추가** |
| Interest / UserInterest | 1순위 (신규) | 회원가입 시 관심 분야 다중 선택 저장용, User와 함께 진행 |
| Book | 1순위 | 프론트 책 검색 컴포넌트가 이미 있어 바로 연동 테스트 가능 |
| BookPhoto | 2순위 | 이미지 업로드(S3) 붙은 뒤 진행. 공유 카드 생성 시 사용자가 선택한 사진(N장) 참조용으로도 쓰임 |
| BookNote | 2순위 | Book CRUD 이후 |
| Group / GroupMember | 3순위 | 공유 탭 기능과 함께. **회원가입 시 "속한 독서모임" 추가도 GroupMember 재사용** (신규 테이블 불필요) |
| ShareRecord / ShareRecordTarget | 3순위 | **`share_type`, `card_image_url`, `public_token` 컬럼 추가** (4번 항목) |
| ~~Like~~ / ~~Comment~~ / ~~Follow~~ | 제외 | Frame 04 변경으로 설계 범위에서 완전히 제외 |

### 3-1. 신규/변경 테이블 상세

**User (컬럼 추가)**

| 컬럼명 | 타입 | NULL | 설명 |
|---|---|---|---|
| gender | VARCHAR(10) | Y | MALE / FEMALE / NONE (선택 안 함 기본) |

**Interest (신규 — 관심 분야 마스터)**

| 컬럼명 | 타입 | 설명 |
|---|---|---|
| id | BIGINT (PK) | |
| name | VARCHAR(30) | 소설, 에세이, 자기계발, 인문, 과학, 경제·경영, 예술, 시 등 |

**UserInterest (신규 — 다대다 매핑)**

| 컬럼명 | 타입 | 설명 |
|---|---|---|
| id | BIGINT (PK) | |
| user_id | BIGINT (FK → User.id) | |
| interest_id | BIGINT (FK → Interest.id) | user_id + interest_id 유니크 |

**ShareRecord (컬럼 추가)**

| 컬럼명 | 타입 | NULL | 설명 |
|---|---|---|---|
| share_type | VARCHAR(20) | N | `book`(독서 기록 공유) / `dashboard`(대시보드 공유) |
| card_image_url | VARCHAR(255) | Y | 생성된 공유 카드 이미지 URL (S3) |
| public_token | VARCHAR(64) | Y | 공개 웹뷰 접근용 UUID 토큰, 비로그인 사용자도 이 값으로 접근 |

> `share_type`이 `book`이면 `book_id` 참조, `dashboard`면 기간(period)·통계 스냅샷을 함께 저장할지는 Step 5에서 상세 설계 (매번 실시간 재계산 vs 스냅샷 저장 트레이드오프 검토 필요)

### Step 5-2 상세 설계 (2026-07-20, 설계 완료 — 구현 전)

Step 5-2 착수 전 사용자에게 4가지를 먼저 확인받음: (1) 카드 이미지 생성 방식 — **"지금은 보류, 클라이언트 캡처 유지"**로 결정, (2) 공개 웹뷰 구현 위치 — **"이 Spring Boot 앱 안에 Thymeleaf로"**(별도 Next.js 서비스로 분리하는 기획서 6장 제안 대신, 현재 백엔드 전용 범위에 맞춰 선택), (3) 카드/웹페이지에 노출할 소감 텍스트 — **"공유 시 기존 BookNote 중 하나를 선택"**, (4) 카드/웹페이지에 노출할 사진 — **"공유 시 원하는 사진 N장 직접 선택"**로 결정. 이 4가지에 따라 이번 설계는 "카드 이미지 자체를 만드는 기능"은 빼고, ① ShareRecord가 어떤 소감/사진을 함께 공유할지 정할 수 있게 데이터 모델을 확장하는 것과 ② 그 데이터를 비로그인 사용자에게 서버 렌더링(Thymeleaf)으로 보여주는 공개 웹페이지로 범위를 좁혔다.

#### 1. 테이블정의서 대비 추가 필요 (원본 xlsx 갱신 필요 항목 누적)

**ShareRecord (컬럼 추가)**

| 컬럼명 | 타입 | NULL | 설명 |
|---|---|---|---|
| book_note_id | BIGINT (FK → BookNote.id) | Y | 카드/공개 페이지에 노출할 소감. shareType=BOOK이고 사용자가 지정했을 때만 값 있음 |
| dashboard_snapshot | TEXT (JSON) | Y | shareType=DASHBOARD일 때 공유 시점의 대시보드 통계를 그대로 얼려서 저장 (3번 참고) |

**ShareRecordPhoto (신규 테이블 — 공유 시 선택한 사진, N:M + 순서)**

| 컬럼명 | 타입 | NULL | 설명 |
|---|---|---|---|
| id | BIGINT (PK) | N | AUTO_INCREMENT |
| share_record_id | BIGINT (FK → ShareRecord.id) | N | |
| book_photo_id | BIGINT (FK → BookPhoto.id) | N | |
| display_order | INT | N | 노출 순서 (0부터) |

`(share_record_id, book_photo_id)` unique — 같은 사진 중복 선택 방지.

#### 2. `POST /api/share-records` 요청/응답 확장

- 요청에 4개 필드 추가: `bookNoteId`(선택, Long), `photoIds`(선택, `List<Long>`, 리스트 순서 = display_order), `dashboardPeriod`(선택, MONTH/QUARTER/YEAR — shareType=DASHBOARD일 때만 의미, 기본 MONTH), `dashboardDate`(선택, yyyy-MM, 기본 이번 달).
- `ShareRecordService`에 교차 검증 추가:
  - `bookNoteId`/`photoIds`는 shareType=BOOK일 때만 허용(DASHBOARD인데 값 있으면 400 INVALID_REQUEST).
  - `bookNoteId`가 있으면 해당 BookNote가 실제로 이 book 소속인지 확인(아니면 400).
  - `photoIds`의 각 사진이 이 book 소속인지 확인(아니면 400), 개수 상한(예: 10장)을 둬서 남용 방지.
  - shareType=DASHBOARD면 기존 `DashboardService.getDashboard(currentUserId, dashboardPeriod, dashboardDate)`를 그대로 재사용해서 나온 결과 중 필요한 값(periodLabel, completedBookCount, totalPagesRead, topGenre, recommendedCaption)만 뽑아 JSON으로 직렬화해 `dashboard_snapshot`에 저장.
  - **왜 스냅샷인가**: 공유 링크는 몇 달 뒤에도 열릴 수 있는데, 그때마다 실시간 재계산하면 "3분기에 5권 완독!"이라고 공유했던 링크가 나중엔 데이터가 바뀌어(책 추가/삭제 등) 다른 숫자를 보여줄 수 있다. 이 문서에 이미 열려 있던 "실시간 재계산 vs 스냅샷 저장" 질문을 이번에 스냅샷 쪽으로 확정.
- 응답(`ShareRecordResponse`)에 `note`(id+content), `photos`(photoId+imageUrl, 순서대로), `dashboardSnapshot` 필드 추가 — 클라이언트가 공유 실행 전 카드 미리보기를 만들 때 그대로 활용 가능.

#### 3. 공개 웹뷰 (`PublicShareController`, Thymeleaf)

- `GET /public/share/{token}` — `ShareRecordRepository.findByPublicToken(token)`(신규 메서드) 없으면 404 안내 페이지.
- shareType=BOOK: 표지, 제목/저자, 선택된 사진(순서대로, 없으면 생략), 선택된 소감(없으면 생략), 독서 기간(시작일~종료일, "9일" 식 일수 표기는 DashboardService의 계산 방식과 동일하게 맞춤 — 공용 유틸로 뽑는 걸 권장).
- shareType=DASHBOARD: `dashboard_snapshot` JSON을 그대로 파싱해서 렌더링(완독 수/페이지 수/최다 장르/추천 문구, 기간 라벨).
- 공유자 닉네임: `User.nickname`이 없으면 "익명의 독서가"로 폴백(프로필 화면 규칙 재사용).
- OG 메타태그(`og:title`/`og:description`/`og:image`/`og:url`) 전부 포함 — `og:image`는 `cardImageUrl`이 있으면 그 값, 없으면 BOOK은 `book.coverImage`, DASHBOARD는 고정 기본 이미지(디자인 에셋 아직 없음 — 준비되는 대로 배치, 지금은 플레이스홀더 경로만 코드에 반영).
- `scope`는 공개 웹페이지 접근 자체와 무관 — `public_token`을 아는 사람은 누구나 열람 가능(기획서 7-4 확정 정책, 이번에 재확인만).
- "이 링크를 아는 사람은 누구나 볼 수 있어요" 안내는 앱(공유 실행 화면) 책임 — 이미 응답에 `scope` 필드가 있어 프론트에서 그대로 판단 가능, 백엔드 변경 불필요.

#### 4. 인프라/설정 변경

- `build.gradle.kts`에 `spring-boot-starter-thymeleaf` 추가 필요(현재 REST 전용이라 없음 — 확인 완료).
- `SecurityConfig.PUBLIC_PATHS`에 `/public/**` 추가.
- 앱 다운로드 CTA(기획서 7-4 열린 질문): 이번에도 보류 — Thymeleaf 템플릿에 나중에 넣을 수 있는 자리만 비워둠, 백엔드 API 계약에는 영향 없음.
- `public_token` 만료/재발급(기획서 7-4 열린 질문): 이번에도 보류 — 필요해지면 `public_token_expires_at` 컬럼 추가로 확장 가능하다는 점만 문서화.
