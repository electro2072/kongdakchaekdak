# 📚 독서 기록 공유 앱 — 개발 현황

## 1. 기술 스택

| 영역 | 선택 |
|---|---|
| 프레임워크 | React Native (TypeScript) |
| 언어 | TypeScript (vanilla, 별도 상태관리 라이브러리 미사용) |
| 도서 검색 API | 알라딘(Aladin) Open API, 카카오(Kakao) 도서 검색 API — 2개 동시 사용 |
| 아키텍처 패턴 | Provider 패턴 — 도서 API를 공통 인터페이스(`BookSearchProvider`)로 추상화 |

## 2. 현재까지 만든 것

**화면설계서 Frame 03(독서 기록 작성)의 요소 1 "책 검색/선택" 컴포넌트**만 구현된 상태입니다. Frame 03의 나머지 요소(별점, 리뷰 입력, 태그, 공개범위+등록)는 아직 없습니다.

### 구현된 컴포넌트 구조

```
BookSearchScreen (화면 루트)
 ├─ SearchBar          : 검색어 입력창 + 검색 버튼
 ├─ BookList           : FlatList 목록, 로딩/빈 상태 처리
 │   └─ BookListItem   : 도서 1권 카드 (표지·제목·저자·출판사)
 └─ useBookSearch (커스텀 훅) : 검색 상태 관리, API 결과를 화면에 연결
      └─ BookService   : 여러 도서 API를 등록/선택해서 호출하는 오케스트레이터
           ├─ AladinApi (BookSearchProvider 구현)
           └─ KakaoApi  (BookSearchProvider 구현)
```

### 파일 구조

```
src/
 ├─ types/
 │   ├─ bookProviderId.ts   # API 제공자 enum (Aladin / Kakao)
 │   ├─ book.ts             # 앱 전체가 공유하는 도메인 타입 Book
 │   └─ bookProvider.ts     # 모든 도서 API가 구현해야 하는 공통 인터페이스
 ├─ services/
 │   ├─ bookService.ts      # provider 등록/선택 오케스트레이터
 │   ├─ aladin/
 │   │   ├─ aladinApi.ts        # 알라딘 fetch 호출 + 도메인 타입 변환
 │   │   └─ aladinApi.types.ts  # 알라딘 원본 응답 타입 (이 API 전용)
 │   └─ kakao/
 │       ├─ kakaoApi.ts         # 카카오 fetch 호출 + 도메인 타입 변환
 │       └─ kakaoApi.types.ts   # 카카오 원본 응답 타입 (이 API 전용)
 ├─ hooks/
 │   └─ useBookSearch.ts    # 검색 상태(books/isLoading/error) 관리 훅
 ├─ components/
 │   ├─ SearchBar.tsx
 │   ├─ BookList.tsx
 │   └─ BookListItem.tsx
 └─ screens/
     └─ BookSearchScreen.tsx
```

### 설계 원칙
- **UI 컴포넌트는 API를 모른다**: `SearchBar`/`BookList`/`BookListItem`은 props만 받고, 네트워크 호출은 전혀 하지 않음
- **API별 원본 타입은 격리**: 알라딘/카카오 각각의 원본 응답 형태(`AladinRawItem`, `KakaoRawDocument`)는 해당 API 폴더 안에서만 쓰이고, 밖으로 나갈 때는 공통 `Book` 타입으로 변환됨
- **API 추가/교체가 쉬움**: 새 도서 API를 붙이려면 `BookSearchProvider` 인터페이스를 구현하는 클래스 하나만 추가하고 `bookService.ts`에 등록하면 됨 (화면/훅 코드 수정 불필요)
- 현재 두 API 모두 등록되어 있고, `search(query, providerId)` 호출 시 `providerId`를 지정해 특정 API를 선택하거나, 지정 안 하면 알라딘이 기본값

## 5. 백엔드 진행 상황 (2026-07-19 기준)

### Step 1. 프로젝트 뼈대 — 완료
- Spring Boot 3.2.5 + Gradle(Kotlin DSL) + Java 17 뼈대 생성
- `application.yml` (MySQL, Docker Compose) + `application-local.yml` (H2, Docker 없이 로컬 실행 확인용) 프로필 분리
- `GET /health` 헬스체크 API

### Step 2. User CRUD — 오늘(2026-07-19) 구현 완료 (Book CRUD는 미착수)
- `domain/user` 패키지: `User` 엔티티, `UserRepository`, `UserService`, `UserController`
- API: `POST /api/users`, `GET /api/users`, `GET /api/users/{id}`, `PATCH /api/users/{id}`, `DELETE /api/users/{id}`
- `common/exception`에 `GlobalExceptionHandler` 추가 — 404(리소스 없음)/400(검증 실패)을 공통 에러 응답 포맷으로 변환
- `config/OpenApiConfig` 추가로 Swagger(`/swagger-ui.html`) 문서에 API 정보 노출
- `UserControllerTest` (MockMvc + H2, `src/test/resources/application.yml`로 테스트 전용 DB 분리) — 생성/조회/수정/삭제/검증 실패 시나리오 커버

**이번 세션에서 판단·결정한 사항 (무인 실행이라 스스로 결정):**
1. 테이블정의서상 `User` 테이블명을 그대로 쓰지 않고 엔티티 `@Table(name = "users")`로 매핑함 — `USER`가 MySQL 예약어라 충돌 방지 목적.
2. 테이블정의서상 `social_provider`/`social_id`는 NOT NULL이지만, Step 3(소셜 로그인)이 아직 없어 지금은 nullable로 완화함. Step 3에서 OAuth2 붙일 때 다시 NOT NULL + unique 제약을 검토해야 함 (코드에 TODO 주석 남김).
3. 닉네임 미입력 시 테이블정의서 설명("미설정 시 랜덤 닉네임 부여")대로 랜덤 닉네임(`책벌레1234` 형태)을 자동 부여하도록 구현.
4. `docs/독서기록앱_백엔드구축계획.md`의 Step 2 체크박스가 실제 코드보다 앞서 모두 체크되어 있던 오류를 바로잡음 (User는 체크, Book은 아직 미구현이므로 체크 해제).

### 검증
- **Gradle 빌드/테스트는 이번 세션에서 실행하지 못함** — 이 샌드박스의 아웃바운드 네트워크가 Maven Central/Gradle Plugin Portal에 접근할 수 없어(proxy 403), `gradle test`가 스프링부트 플러그인조차 받아오지 못하고 실패함. 코드는 작성 후 정적으로 재검토(임포트/시그니처/괄호 짝 확인)만 수행함. **다음 세션에서 Maven Central 접근이 가능한 환경(또는 로컬 개발 환경)에서 `./gradlew test` 실행 확인이 필요함.**
- 프론트엔드는 이번 세션에서 변경하지 않음 (`npm run typecheck` 실행 대상 없음).
