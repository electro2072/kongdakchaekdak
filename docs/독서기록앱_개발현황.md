## 2. 현재까지 만든 것

**화면설계서 Frame 03(독서 기록 작성)의 요소 1 "책 검색/선택" 컴포넌트**만 구현된 상태입니다. Frame 03의 나머지 요소(별점, 리뷰 입력, 태그, 공개범위+등록)는 아직 없습니다.

### 구현된 컴포넌트 구조

```
BookSearchScreen (화면 루트)
 ├─ SearchBar          : 검색어 입력창 + 검색 버튼
 ├─ BookList           : FlatList 목록, 로딩/빈 상태 처리
 │   └─ BookListItem   : 도서 1권 카드 (표지·제목·저자·출판사)
 └─ useBookSearch (커스텀 훅) : 검색 상태 관리, API 결과를 화면에 연결
      └─ BookService   : 여러 도서 API를 등록/선택해서 호출하는 오케스트레이터
           ├─ AladinApi (BookSearchProvider 구현)
           └─ KakaoApi  (BookSearchProvider 구현)
```

### 파일 구조

```
src/
 ├─ types/
 │   ├─ bookProviderId.ts   # API 제공자 enum (Aladin / Kakao)
 │   ├─ book.ts             # 앱 전체가 공유하는 도메인 타입 Book
 │   └─ bookProvider.ts     # 모든 도서 API가 구현해야 하는 공통 인터페이스
 ├─ services/
 │   ├─ bookService.ts      # provider 등록/선택 오케스트레이터
 │   ├─ aladin/
 │   │   ├─ aladinApi.ts        # 알라딘 fetch 호출 + 도메인 타입 변환
 │   │   └─ aladinApi.types.ts  # 알라딘 원본 응답 타입 (이 API 전용)
 │   └─ kakao/
 │       ├─ kakaoApi.ts         # 카카오 fetch 호출 + 도메인 타입 변환
 │       └─ kakaoApi.types.ts   # 카카오 원본 응답 타입 (이 API 전용)
 ├─ hooks/
 │   └─ useBookSearch.ts    # 검색 상태(books/isLoading/error) 관리 훅
 ├─ components/
 │   ├─ SearchBar.tsx
 │   ├─ BookList.tsx
 │   └─ BookListItem.tsx
 └─ screens/
     └─ BookSearchScreen.tsx
```

### 설계 원칙
- **UI 컴포넌트는 API를 모른다**: `SearchBar`/`BookList`/`BookListItem`은 props만 받고, 네트워크 호출은 전혀 하지 않음
- **API별 원본 타입은 격리**: 알라딘/카카오 각각의 원본 응답 형태(`AladinRawItem`, `KakaoRawDocument`)는 해당 API 폴더 안에서만 쓰이고, 밖으로 나갈 때는 공통 `Book` 타입으로 변환됨
- **API 추가/교체가 쉬움**: 새 도서 API를 붙이려면 `BookSearchProvider` 인터페이스를 구현하는 클래스 하나만 추가하고 `bookService.ts`에 등록하면 됨 (화면/훅 코드 수정 불필요)
- 현재 두 API 모두 등록되어 있고, `search(query, providerId)` 호출 시 `providerId`를 지정해 특정 API를 선택하거나, 지정 안 하면 알라딘이 기본값

## 7. 프론트엔드 네이티브 스캐폴드 생성 (2026-07-19)

기존 `frontend/`에는 `src/` 로직 레이어만 있고 실제로 실행 가능한 React Native 프로젝트(android/ios 폴더)가 없었다. 사용자가 Android Studio를 설치한 김에 `npx react-native init`(0.74.0)으로 실제 android/ios 네이티브 프로젝트를 생성하고, 기존 `src/`를 그대로 이식해서 `App.tsx`가 `BookSearchScreen`을 렌더링하도록 연결했다.

- 이 세션(클라우드 샌드박스)에서 `npm install`, `npm run typecheck`, `npx jest` 모두 통과 확인함 (npm 레지스트리는 이 샌드박스에서도 접근 가능했음)
- 다만 실제 Android 빌드/에뮬레이터 실행은 Gradle의 Android용 의존성(Google Maven 등)이 필요해서 이 샌드박스에서는 확인 못 함 — 사용자 로컬(Android Studio + 에뮬레이터)에서 확인 필요했음

### ✅ 로컬 Android 빌드/실행 검증 완료 (2026-07-19)
사용자 컴퓨터에 Android Studio 설치 + 에뮬레이터(AVD) 생성 후 `npm run android`로 실제 빌드/설치/실행까지 확인함.
- 트러블슈팅: Windows Defender가 Gradle 캐시 이동을 막아서(`AccessDeniedException`) 프로젝트 폴더를 예외 처리로 등록해 해결, `local.properties`에 `sdk.dir` 설정, `platform-tools`를 PATH에 추가해서 `adb` 인식되게 해결
- 에뮬레이터에서 책 검색 화면(`BookSearchScreen`)이 정상 렌더링되는 것을 스크린샷으로 확인함 (검색창/버튼/빈 상태 문구 모두 의도대로 표시). 알라딘/카카오 API 키가 아직 없어 실제 검색 결과는 비어있는 게 정상.
- 이걸로 백엔드(Step 1~2, gradle test 통과)에 이어 프론트엔드도 로컬 환경에서 end-to-end 실행 검증 완료.

### ⚠️ 프론트엔드 작업 일시 중단 (2026-07-19)
사용자 로컬 디스크에서 `src/navigation/`, `AuthContext.tsx`, `RootNavigator.tsx` 등 이 세션이 작성하지 않은 네비게이션/인증 화면 코드가 발견됨 (git에는 없고 로컬에만 존재, `react-native-screens` 등 미설치 패키지를 참조해 Metro 에러 유발). 다른 자동 세션(매일 새벽 6시 예약 작업으로 추정)이 동시에 프론트엔드를 건드리고 있을 가능성이 있어, 사용자가 **"frontend 작업을 중단하고 backend 작업을 하라"**고 명시적으로 지시함. 이후 세션은 **사용자가 별도로 재개를 요청하기 전까지 `frontend/` 디렉터리를 건드리지 않을 것**. ## 8. Step 3 인증 — 이메일/PW 로그인 (2026-07-19, 사용자 지시로 백엔드 전환 후 구현)

### 구현 내용
- `domain/user/User.java`: `passwordHash` 컬럼 추가 + `forLocalSignup(nickname, email, encodedPassword)` 팩토리 메서드. 이메일/PW 로그인은 별도 `email` 컬럼을 새로 만들지 않고 기존 `socialProvider="local"`, `socialId=이메일`로 저장(테이블정의서 변경 최소화 목적).

## 10. 카카오/구글/네이버 소셜 로그인 코드 선반영 (2026-07-19)

사용자가 아직 카카오/구글/네이버 앱 등록(Client ID/Secret 발급)을 하지 않은 상태에서, "오늘 안에 `backend/.env` 파일을 만들어둘 테니 그걸 전제로 코드를 미리 만들어달라"고 요청해서 실제 로그인 연동 코드를 먼저 구현함.

### 설계
- **패턴**: 모바일 앱(React Native)이 각 제공자의 공식 SDK로 이미 로그인해서 토큰을 받아오고, 그 토큰을 백엔드로 넘기면 백엔드는 그 토큰이 진짜인지 제공자 API에 물어봐서 확인만 하는 방식. 카카오/네이버는 "access token"을 쓰고(`Authorization: Bearer` 로 사용자 정보 API 호출), 구글은 "ID token"을 쓰는 게 표준이라 방식이 다르다 — 각 API 실제 응답 형식은 웹 검색으로 확인 후 구현함(카카오 `v2/user/me`, 네이버 `v1/nid/me`, 구글 `tokeninfo?id_token=`).
- 구글은 `aud`(발급 대상) 클레임을 `GOOGLE_CLIENT_ID`와 반드시 비교해야, 다른 앱을 위해 발급된 구글 토큰으로 우리 백엔드에 로그인하는 걸 막을 수 있음 — 이 검증을 넣었고, `GoogleOAuthClientTest`로 단위 테스트까지 작성함.
- 구글의 `tokeninfo` 엔드포인트는 구글 공식 문서가 "개발/디버깅용, 프로덕션에서는 요청 제한 있음"이라고 명시함 — 지금은 MVP 단계라 이 방식으로 우선 구현했고, **실 사용자가 늘면 `google-api-client` 라이브러리 기반 서명(JWK) 검증으로 교체 필요** (TODO).

### 구현 내용
- `domain/auth/oauth2` 패키지(신규): `KakaoOAuthClient`/`GoogleOAuthClient`/`NaverOAuthClient`(각 제공자 사용자 정보 API 호출), `SocialUserInfo`(공통 결과 DTO), `KakaoOAuthProperties`/`GoogleOAuthProperties`/`NaverOAuthProperties`(`app.oauth2.*` 바인딩), `OAuth2Config`(타임아웃 5초 설정한 공용 `RestTemplate` 빈).
- `domain/auth/SocialAuthService`(신규): 제공자별 로그인 메서드 3개 → 공통 find-or-create 로직 → `AuthService.issueToken()` 재사용해서 우리 앱 JWT 발급 (이메일/PW와 동일한 토큰 포맷).
- `AuthController`에 `POST /api/auth/kakao`, `/google`, `/naver` 추가 (각각 `SocialAccessTokenRequest`/`GoogleIdTokenRequest` DTO).
- `SecurityConfig`의 `PUBLIC_PATHS`에 위 3개 경로 추가 (로그인 엔드포인트라 인증 없이 호출 가능해야 함).

## 11. 리소스 소유자 검증 강화 (2026-07-20)

로그인만 되어 있으면 다른 회원의 프로필/책도 수정·삭제할 수 있던 문제를 막기 위해, User/Book의 쓰기(수정/삭제) API에 "본인 소유 리소스인지" 검증을 추가함. 조회(단건/목록) API는 공유 앱 특성상 의도적으로 계속 열어둠 (다른 사람의 프로필/독서 기록을 구경하는 것 자체가 기능).

### 구현 내용

## 12. Step 4 — 이미지 업로드 (S3 presigned URL, BookPhoto API) (2026-07-20)

책 상세 페이지의 장소 사진(BookPhoto, 테이블정의서 기준) 업로드/조회/삭제 API를 구현함. 실제 사진 데이터는 이 서버를 거치지 않고 클라이언트가 S3에 직접 업로드하는 presigned URL 방식을 사용 — 서버는 업로드 URL 발급과 메타데이터(위치/좌표) 저장만 담당한다.

### 설계 — 2단계 업로드 흐름
1. `POST /api/books/{bookId}/photos/presigned-url` — 파일명/Content-Type을 보내면 S3에 직접 PUT할 수 있는 presigned URL(기본 10분 유효)과, 업로드 완료 후 접근 가능한 공개 URL(`imageUrl`)을 함께 발급받음.
2. 클라이언트가 그 URL로 S3에 직접 업로드.
3. `POST /api/books/{bookId}/photos` — 1번에서 받은 `imageUrl`(+ 위치/좌표)을 보내 실제 DB 레코드를 생성. presigned URL 발급만으로는 DB에 아무것도 기록되지 않음.

### 구현 내용
- `config/S3Properties`(`app.s3.*` 바인딩: bucket/region/accessKey/secretKey/presignedUrlExpirationSeconds) + `config/S3Config`(`S3Presigner` 빈 등록, `StaticCredentialsProvider`/`AwsBasicCredentials` 사용).
- `domain/bookphoto` 패키지(신규): `BookPhoto` 엔티티(테이블정의서 그대로 — image_url/location_text/latitude/longitude, updated_at은 없음), `BookPhotoRepository`, `BookPhotoService`, `BookPhotoController`.
- API: `POST /api/books/{bookId}/photos/presigned-url`(발급), `POST /api/books/{bookId}/photos`(등록), `GET /api/books/{bookId}/photos`(목록 조회), `DELETE /api/books/{bookId}/photos/{photoId}`(삭제).
- 등록/삭제는 본인 소유 책에 대해서만 가능(Step 3 소유자 검증과 동일한 `ForbiddenException`/403 패턴 재사용). 조회는 User/Book과 동일한 원칙으로 열어두되, `bookId` 자체가 URL 경로상 리소스 식별자라 존재하지 않는 책이면 404.
- S3 key는 원본 파일명을 그대로 쓰지 않고 확장자만 추출해서 `book-photos/{bookId}/{UUID}.{ext}` 형태로 생성 — 경로 조작(`../../`) 및 특수문자 문제 방지.
- Content-Type은 `image/*` 형식만 허용하도록 요청 DTO에 검증 추가 (임의 파일 업로드 방지).
- `build.gradle.kts`: `software.amazon.awssdk:bom:2.47.4` + `software.amazon.awssdk:s3` 추가 (S3Presigner는 실제 AWS 네트워크 호출 없이 로컬에서 서명만 계산하므로 별도 HTTP 클라이언트 의존성 불필요).
- `backend/.env.example`에 `AWS_S3_BUCKET`/`AWS_S3_REGION`/`AWS_ACCESS_KEY_ID`/`AWS_SECRET_ACCESS_KEY` 자리 추가.
- `BookPhotoControllerTest` 추가 — presigned URL 발급, 이미지가 아닌 Content-Type 거부(400), 등록/조회/삭제 전체 흐름, 존재하지 않는 책 조회 시 404, 다른 사람 책에 등록/삭제 시도 시 403, 토큰 없이 요청 시 401 커버. **S3Presigner는 실제 AWS 호출 없이 로컬 서명만 하므로 `@MockBean` 없이 테스트 전용 더미 자격증명(`src/test/resources/application.yml`)으로 실제 SDK 로직까지 검증함.**

### 판단·결정 사항
1. presigned URL이 가리키는 공개 URL은 표준 virtual-hosted-style(`https://{bucket}.s3.{region}.amazonaws.com/{key}`)로 계산해서 응답에 포함 — 버킷이 퍼블릭 읽기이거나 앞단에 CDN을 두는 것을 전제로 함. 버킷을 private로 유지하기로 하면 이 URL 생성 로직을 CloudFront 서명 URL 등으로 교체해야 함(Step 5-2 공유 카드/공개 웹뷰 설계 시 재검토 필요, 코드에 TODO 남김).
2. IAM 사용자는 해당 버킷에 대한 `s3:PutObject` 권한만 있으면 충분(최소 권한) — `.env.example`에 안내 문구 추가.
3. accessKey/secretKey가 비어 있어도(.env 작성 전) 서버 기동 자체는 정상 — 실제 presigned URL 발급을 호출하는 시점에만 실패함 (OAuth2 소셜 로그인과 동일한 완화 원칙).

## 13. Step 5 — 소감/공유 기능 (BookNote, Group, ShareRecord API) (2026-07-20)

Step 5 착수 전 사용자에게 두 가지를 먼저 확인받음: (1) ShareRecord의 scope(전체/그룹/커스텀공개)를 이번에 실제 열람 권한 제어까지 구현할지 — **"우선 기록용으로만 구현"**로 결정, (2) 카드 이미지 생성 + 공개 웹뷰(계획서 Step 5-2)를 이번에 함께 할지 — **"나중에"**로 결정(이미 이전에도 그렇게 정했었다고 확인). 이 두 결정에 따라 이번 Step 5는 BookNote/Group/ShareRecord의 CRUD/기록 생성까지만 구현하고, 실제 공개 열람 제어와 카드 이미지·공개 웹뷰는 Step 5-2로 명확히 분리해서 남겨둠.

### 설계 중 발견한 테이블정의서 빈틈
`ShareRecord` 테이블에 "누가 공유했는지"를 나타내는 컬럼이 원래 없었음 — `book_id`로 `book.user`를 타면 알 수 있어 보이지만, `share_type=dashboard`(대시보드 공유)는 애초에 `book_id`가 NULL이라 그 방법으로는 공유자를 알 수 없음. Step 3에서 `User.password_hash`를 테이블정의서 없이 추가했던 것과 같은 방식으로, **`ShareRecord`에 `user_id`(공유한 사용자) 컬럼을 추가**해서 진행함. "마이페이지 공유 이력"이 본인 것만 보여야 하고, 삭제 권한 체크도 필요해서 필수적인 컬럼이었음. **원본 `독서기록앱_테이블정의서.xlsx`에 이 컬럼 추가 반영이 필요함.**

### 구현 내용
- **BookNote** (`domain/booknote`): 책에 대한 소감 CRUD, 한 책에 여러 번 작성 가능. `POST/GET /api/books/{bookId}/notes`, `PATCH/DELETE /api/books/{bookId}/notes/{noteId}`. 작성/수정/삭제는 본인 소유 책만 가능(Book/BookPhoto와 동일한 `ForbiddenException` 패턴), 조회는 열어둠.
- **Group/GroupMember** (`domain/group`): 독서모임/가족 등 그룹. `POST/GET /api/groups`, `GET/PATCH/DELETE /api/groups/{id}`, `GET/POST /api/groups/{id}/members`, `DELETE /api/groups/{id}/members/{userId}`. 그룹 생성자가 소유자+자동 첫 멤버가 되고, 그룹명 수정/삭제/멤버 추가는 소유자만 가능. 멤버 제거(탈퇴)는 본인 스스로 또는 소유자가 할 수 있으나, **소유자 본인은 탈퇴할 수 없음**(그룹이 주인 없는 상태가 되는 것을 막기 위함 — 그 대신 그룹 삭제를 사용해야 함). 그룹명은 테이블정의서에 `groups`로 매핑(`GROUP`이 SQL 예약어라 `User`→`users`와 동일한 이유).
- **ShareRecord/ShareRecordTarget** (`domain/share`): 공유 기록 생성/조회(본인 것만)/삭제. `POST/GET /api/share-records`, `DELETE /api/share-records/{id}`. `share_type`(book/dashboard), `scope`(all/group/custom), `platform`(app/instagram/threads/tiktok), `target_type`(user/group) 모두 Book.status와 동일한 `@Converter(autoApply=true)` 패턴으로 소문자 DB 값과 매핑. 생성 시 교차 검증: shareType=BOOK이면 bookId 필수+본인 소유 책만, scope=GROUP/CUSTOM이면 targets 최소 1개 필요(GROUP은 전부 targetType=GROUP), scope=ALL이면 targets 무시. GROUP 타입 타겟은 공유자가 그 그룹의 소유자/멤버여야만 허용(남의 그룹에 공유 방지). `public_token`은 생성 시 항상 UUID로 자동 발급(실제로 쓰는 공개 웹뷰 라우트는 Step 5-2에서 추가 예정). `ShareRecordTarget.targetId`는 `target_type`에 따라 User 또는 Group을 가리키는 다형 참조라 DB FK 없이 애플리케이션 레벨에서만 검증(테이블정의서에도 FK 컬럼 없음).
- 새 공통 예외 `InvalidRequestException`(400, error: `INVALID_REQUEST`) 추가 — 단일 필드 검증(`@Valid`)으로 표현 안 되는 교차 필드 검증(예: "shareType=BOOK이면 bookId 필수") 전용.
- `BookNoteControllerTest`/`GroupControllerTest`/`ShareRecordControllerTest` 3개 신규 — 각 도메인의 정상 흐름 + 소유자 검증(403)/중복(409)/교차검증실패(400)/401 시나리오 커버.

### 판단·결정 사항
1. (사용자 확인) scope는 지금은 기록용으로만 — Book/BookNote 조회 API는 계속 전체공개 유지, 실제 "그룹공개/커스텀공개면 못 보게" 하는 권한 제어는 나중에.

3. ShareRecord에 테이블정의서에 없던 `user_id` 컬럼 추가 (위 "빈틈" 참고) — 원본 xlsx 갱신 필요.
4. GROUP scope의 target은 전부 targetType=GROUP만 허용, CUSTOM scope는 USER/GROUP 혼합 허용 — scope와 target 타입 조합 규칙을 이렇게 정함.
5. 그룹 소유자는 자기 그룹에서 탈퇴 불가(그룹 삭제로 유도) — 소유자 없는 그룹이 생기는 것을 막기 위한 선택.

## 14. Step 5-1 — 독서 대시보드(Recap) 통계 (2026-07-20)

사용자가 "화면이 복잡한 만큼 백엔드도 설계가 필요해 보여요"라고 직접 짚어준 대로, 구현 전에 기획서 3-6-1(독서 대시보드/Recap)과 4-5, 화면설계서 Frame 05.1의 요구사항을 먼저 다시 읽고 설계를 정리한 뒤 구현함.

### 구현 내용
- `domain/dashboard` 패키지(신규): `DashboardPeriod` enum(MONTH/QUARTER/YEAR), `DashboardService`(핵심 집계 로직), `DashboardController`(`GET /api/dashboard`), `dto/` 5종(`DashboardResponse`, `GenreRatioDto`, `MonthlyTrendDto`, `DashboardHighlights`, `BookHighlightDto`).
- **자체 테이블을 만들지 않고** 매 요청마다 `Book` 데이터를 실시간 집계하는 방식으로 구현 — 현재 데이터 규모에서는 캐싱/배치 집계 테이블이 과함. 사용자·데이터가 늘어 성능 문제가 생기면 그때 캐싱 테이블 도입을 재검토하기로 함(코드 주석에 남김).
- `BookRepository`에 `findByUserIdAndStatusAndEndDateBetween(userId, status, start, end)` 추가 — 헤드라인 통계 구간과 추이 그래프 구간을 한 번에 커버하는 합집합 범위로 조회한 뒤, 메모리에서 두 용도로 각각 필터링.
- 쿼리 파라미터: `period`(month/quarter/year, 기본 month), `date`(yyyy-MM, 생략 시 이번 달). 항상 JWT 주체(`@AuthenticationPrincipal Long currentUserId`) 본인 통계만 조회 — 다른 회원 대시보드 조회 API는 없음(마이페이지 개인 기능이라 필요 없음).
- 완독 수 / 읽은 페이지 수(totalPages 합, null은 0 취급) / 장르별 비율(도넛 차트용, 비율은 소수 첫째 자리 반올림, 장르 없는 책은 "기타"로 집계) / 월별 완독 추이(막대그래프용) / 하이라이트(최다 장르, 최장·최단 완독 기간 책) / 추천 공유 문구를 모두 한 응답에 담음.
- **월별 완독 추이는 선택한 기간 종류(월간/분기별/연간)와 무관하게 항상 "선택 기간의 마지막 달 기준 직전 6개월"로 고정** — 연간을 선택해도 그래프는 여전히 6개월치만 보여줌(화면설계서 Frame 05.1이 요구하는 그래프 형태를 그대로 반영).
- 완독 기간(일수)은 화면설계서 서재 탭의 "9일" 표기와 동일하게 시작일~종료일을 양 끝 포함해서 계산(예: 06.20~06.28 = 9일).
- 추천 공유 문구는 완독 수가 0이면 격려 문구, 아니면 "{이번 달|이번 분기|올해} N권 완독! {캐치프레이즈}" 형태 — 캐치프레이즈는 기획서 1장 문구를 그대로 재사용하되, `Math.random()` 등 비결정적 요소 없이 완독 수를 나머지 연산(`% 배열길이`)해서 결정론적으로 골라 테스트에서 정확한 문자열을 검증할 수 있게 함.
- `DashboardControllerTest` 추가 — 4권의 책(7월 3권 + 6월 1권) 픽스처로 월간/분기별/연간 집계, 완독 0권일 때 격려 문구, `date` 생략 시 이번 달 기본값, 토큰 없이 401 시나리오를 커버.

### 판단·결정 사항
1. 자체 통계 테이블 없이 매 요청 실시간 집계 — 스키마 변경/배치 작업 없이 빠르게 구현 가능하고, 현재 데이터 규모에서 충분히 빠름. 확장 필요 시 캐싱/배치 집계 테이블 도입 재검토.
2. 추이 그래프는 항상 마지막 달 기준 직전 6개월 고정(기간 종류 무관) — 화면설계서 그래프 형태를 그대로 따름.
3. 장르 없는(null/공백) 책은 "기타"로 묶어서 집계 — 테이블정의서상 genre가 선택 입력이라 빈 값이 있을 수 있음.
4. 완독 기간 동률 시 tie-break는 항상 id가 더 작은(먼저 등록된) 책 우선 — 최장/최단 모두 동일한 규칙 적용.
5. 대시보드는 마이페이지 개인 기능이라 본인 것만 조회 가능 — 타인 대시보드 열람 API는 만들지 않음(ShareRecord의 share_type=dashboard로 "공유"는 별도 경로, Step 5-2에서 공개 웹뷰로 이어질 예정).

### 검증
- 이번에도 Gradle 실행 불가 — 리뷰 서브에이전트가 특히 날짜 연산 정확성에 집중해서 검토: 분기 경계 계산(1~4분기 전부), 월간/분기별/연간 각 경우의 6개월 추이 윈도우 계산, 헤드라인 구간과 추이 구간의 합집합 쿼리 범위가 양방향(추이가 더 넓은 경우/기간이 더 넓은 경우) 모두 올바른지, 동률 tie-break 비교자가 max()/min() 양쪽 모두에서 실제로 "더 작은 id"를 고르는지, 테스트 픽스처의 손계산 기대값이 실제 로직과 일치하는지를 전부 확인했고 이슈 없음으로 확인됨.
- **다음 세션/사용자가 로컬에서 꼭 확인해야 함**: `gradle test`(신규 `DashboardControllerTest`), Swagger/Postman에서 `GET /api/dashboard?period=month`, `?period=quarter`, `?period=year` 등을 실제 데이터로 호출해 화면설계서 Frame 05.1과 응답 형태가 맞는지 눈으로 한 번 확인.

## 15. Step 5-2 설계 (공유 카드 + 공개 웹뷰) (2026-07-20, 설계만 진행 — 구현 전)

사용자가 "step 5-2 에 필요한 설계 먼저 진행해 주세요"라고 요청해서, 코드 작성 없이 설계만 먼저 정리함. 착수 전 4가지 핵심 결정을 사용자에게 직접 확인받음.

### 사용자 확인 사항
1. **카드 이미지 생성 방식** — "지금은 보류, 클라이언트 캡처 유지"로 결정. (다른 선택지였던 "서버 Java 2D 렌더링"이나 "헤드리스 브라우저(HTML→이미지)"는 채택하지 않음.) 즉 서버가 카드 이미지를 직접 그려주는 기능은 이번 Step 5-2 범위에서 완전히 제외되고, `ShareRecord.cardImageUrl`은 계속 클라이언트가 만든 이미지 URL을 선택적으로 받는 필드로만 남는다. → 이 결정 덕분에 Step 5-2 범위가 크게 좁아짐(무거운 이미지 렌더링 인프라 불필요).
2. **공개 웹뷰 구현 위치** — "이 Spring Boot 앱 안에 Thymeleaf로" 결정. 기획서 6장이 제안한 "별도 Next.js 웹 서비스로 분리"는 채택하지 않음 — 지금은 프론트엔드 작업이 중단된 상태(사용자의 별도 지시)라 새 프론트엔드 프로젝트를 만드는 대신, 이미 백엔드구축계획 문서에 예정돼 있던 Thymeleaf 서버 렌더링 방식을 그대로 택함.
3. **카드/웹페이지 소감 텍스트** — "공유 시 기존 BookNote 중 하나를 선택"으로 결정. (공유 시점에 새 caption을 입력받는 방식, 소감 없이 책 정보만 노출하는 방식은 채택하지 않음.)
4. **카드/웹페이지 사진** — "공유 시 원하는 사진 N장 직접 선택"으로 결정. (자동으로 최근 등록 사진만 보여주는 방식, 사진 없이 표지만 노출하는 방식은 채택하지 않음.)

### 설계 중 추가로 판단한 사항 (사용자 확인 없이 기술적 필요에 따라 결정, 백엔드구축계획 문서에 상세 근거 기록)
- **대시보드 공유는 스냅샷으로 얼려서 저장** — `share_type=dashboard`인 ShareRecord는 공유 시점의 통계(완독 수/페이지 수/최다 장르/추천 문구/기간 라벨)를 `dashboard_snapshot`(JSON) 컬럼에 그대로 저장하기로 함. 실시간 재계산 방식은 몇 달 뒤 링크를 열었을 때 그 사이 데이터가 바뀌면 공유 당시와 다른 숫자가 보일 수 있어 부적절하다고 판단(백엔드구축계획 문서에 예전부터 열려 있던 질문이었음).
- **소감/사진 선택을 위한 스키마 확장** — 테이블정의서에 없는 `ShareRecord.book_note_id`(FK)와 신규 테이블 `ShareRecordPhoto`(share_record_id/book_photo_id/display_order)를 추가하기로 함. Step 5의 `ShareRecord.user_id` 추가와 동일한 패턴 — 사용자가 확정한 기능(소감/사진 선택)을 구현하려면 스키마 확장이 필수적이었음. **원본 `독서기록앱_테이블정의서.xlsx`에 반영 필요 (이월 항목에 추가).**
- **공개 웹뷰 접근 정책**: 기획서 7-4에서 이미 확정돼 있던 "public_token을 아는 사람은 scope와 무관하게 접근 가능" 정책을 재확인만 하고 그대로 유지 — Step 5-2에서 별도 열람 권한 제어를 추가하지 않음.
- **앱 다운로드 CTA / 토큰 만료 정책**(기획서 7-4의 "열린 질문" 2가지)은 이번에도 보류 — 지금 결정하지 않아도 백엔드 API 계약에 영향이 없어서, 실제 구현 시점 또는 배포 임박 시점에 다시 논의하기로 함.

### 상세 설계 문서화 위치
전체 데이터 모델(컬럼/테이블 상세), API 요청·응답 확장안, `PublicShareController`/Thymeleaf 설계, 인프라 변경사항(Thymeleaf 의존성, SecurityConfig), 구현 순서 7단계는 모두 `독서기록앱_백엔드구축계획.md`의 "Step 5-2 상세 설계" 절에 기록해둠 — 다음 세션은 그 문서를 그대로 따라 구현하면 됨.
